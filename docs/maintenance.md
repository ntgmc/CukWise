# CukWise 日常维护

网站采用静态数据。编辑资料后先检查，再推送 `main`；Pages 工作流会通过类型、数据、单元和浏览器检查后发布。

## 每次更新

1. 确认具体型号、版本、接口、线长及套装。优先使用官网规格图和产品标注；评测只补同型号、注明条件的实测；汇总表列值注明表格日期和型号，不改写成实测。
2. 按下表修改源文件，保留原来的记录 ID。价格增加新记录，不覆盖旧活动条件。
3. 运行 `npm run check`。涉及界面、推荐或路径时，再运行 `npm run test:e2e`。
4. GitHub Pages 采用子路径部署。发布前使用 `SITE_URL=https://ntgmc.github.io BASE_PATH=/CukWise npm run check`，然后 `BASE_PATH=/CukWise npm run test:e2e`。
5. 审查 diff，推送 `main`，确认 Pages 工作流成功，再打开线上相应页面。

| 更新内容 | 文件 | 要核对的内容 |
| --- | --- | --- |
| 新品与规格 | `src/data/products.json` | 型号、单口固定 PD、输入、重量口径、不同接口、多口分配 |
| 主图与规格图 | `public/images/products/`、`sources.json` | 本地 WebP；主图 720 × 520 透明画布；图片原址与产品来源 |
| 活动价或参考价 | `src/data/prices.json` | 日期、平台、店铺、资格、用券、有效期、原图或原文 |
| 官网购买入口 | `src/data/purchase-links.json` | 对应准确型号和套餐；移除联盟、活动追踪参数 |
| 外部资料 | `src/data/readings.json` | 作者、日期、资料类型、正文实际覆盖的产品 |
| 评测摘要 | `src/data/reviews.json` | 原文设备、测试接口、模式、样品和测试条件 |
| 站内指南 | `src/data/guides.ts` | 分类、建议理由、产品关联、来源、核对日期 |

`npm run data:audit` 输出各品类的产品、报价和资料覆盖，列出核心参数缺口与未关联报价，可重定向保存为 Markdown。审计只读数据，标准款和限定款分开统计，按品类检查适用字段；小配件单独核对。

`npm run data:check` 输出资料数量、购买入口覆盖、已有报价的产品数量及尚未明确型号的报价数。新增产品时同步更新浏览器测试中总产品数；新增价格时同步更新对应类型的数量断言。截图报价导入的 74 条固定原件检查应保留。

## 每周来源检查

`.github/workflows/sources.yml` 在每周一执行，也支持 GitHub Actions 手动运行。报告在该次工作流 Summary 和 `source-availability` 附件中，保留 30 天。可以本地运行：

```sh
npm run sources:check
```

结果写入忽略的 `artifacts/maintenance/sources.json` 和 `sources.md`，不改任何资料。状态含义：

- `reachable`：链接可访问；正文与规格另行核对。
- `needs-browser`：登录、验证码、403 或限流，需要正常浏览器核对。
- `missing`：404、410 或已识别的 HTTP 200 失效页，优先找原站新地址。
- `unavailable`：网络超时或其他服务异常，下次核对，不能据此删掉来源。

检查覆盖产品来源、外部文章、摘要和指南的来源。店铺页面与实时价格仍需人工核对；官网购买入口与活动价可能属于不同店铺或套餐。

## 数据判断规则

- 未核实数值用 `null`，文本用空字符串，不能填 0 或根据同系列推算。不同版本各自建档。
- `pdOutputW` 是可确认的单口固定 PD 档。小米私有快充、PPS 和整机总功率保存在相应字段或 `specs`，不要覆盖固定 PD。
- AC 输入、Turbo 模式、接口及多口分配必须保留。例如 BA652U 普通模式与 Turbo 功率不同；TA1406U 自带线与 C2 的上限不同。
- `kind: "deal"` 才可参与好价计算。发布价、首发报道和表格预期价保留 `reference`，不能按旧价格承诺当前可买。
- PPS / 小米协议支持不等于某机型达到最高快充；没有实测时不写“满血”或百分比匹配。
- 视频只拿到作者的原文入口时，标记 `video`，简介描述入口和主题，不宣称已观看或验证视频结果。
- 摘要用自己的短句说明原文重点，保留作者与原文，避免整篇复制。不要写成本站实测或虚构用户体验。

## 参数字段统一

`src/lib/specifications.ts` 定义统一字段的分组和顺序，产品详情与对比共用这套顺序。维护 `products.json` 时直接填写统一字段；校验会拒绝旧的同义名称，避免对比表再次出现重复空行。

| 原字段 | 统一后的填写方式 |
| --- | --- |
| `USB-C 输出`、`USB-C1 / C2 输出` | 分别填写 `USB-C1 输出`、`USB-C2 输出`，确认为相同档位时各自记录完整条件 |
| `USB-A 输出`、`USB-C3 / USB-A 输出` | 分别填写 `USB-A1 输出`、`USB-C3 输出`；多 A 口保留 A1 / A2 的差别 |
| `USB-C 伸缩线输出`、`USB-C1 自带线输出` | `自带 USB-C 线输出`，保留“伸缩线”和官方 C1 标号；Lightning 自带线单列 |
| `多口总输出`、`双口总输出`、`三口总输出`、`多口输出` | 合入 `多口输出`，用“总功率 / 双口总功率 / 三口总功率 / 分配与条件”注明口径，不将分配推算成总功率 |
| `线长`、`自带线长度`、`电源线长度`、`配套 DC 线长度` | `线材长度`，逐行注明数据线、自带线、电源线或配套 DC 线 |
| `电量显示`、`显示方式`、`显示功能` | `显示功能`；屏幕尺寸与类型使用 `屏幕规格` |
| `重量说明`、`重量口径` | `重量口径`，保留是否含底座、线材、屏幕与实测来源 |
| `配色`、`产品颜色` | `产品颜色` |
| `线材`、`线材设计` | `线材设计` |
| `认证`、`认证信息` | `认证信息`，保留认证类型、编号及核对条件 |
| `接口类型` 与顶层 `ports` | 合并到 `ports`，线材接口统一使用“转”，保留转接头等套装差别 |

仅有一个且未编号的 USB-C / USB-A 插口在表中记为 C1 / A1；已有官方编号继续保留。自带线不占用普通插口编号。例如 TA1406U 的 C1 是伸缩线，应写在自带线字段，C2 / C3 仍使用原编号。没有明确的输出资料时不从接口数推定功率，也不把未单列字段的“—”当成没有该功能。

输入与输出、单口与多口、固定 PD 与私有档、二合一的充电器 / 充电宝 / Turbo 模式各自保留。新类型参数可以新增字段，登记到统一分组后再运行 `npm run check`。

## 发布后快速检查

打开首页、产品库、一个有价格记录的产品页、一个指南页；检查图片、参考价标签、筛选刷新、对比入口。手机宽度下确认导航可滚动、正文没有横向溢出。留意浏览器控制台中的 hydration 或运行错误。
